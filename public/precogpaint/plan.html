Context

The finding in FINDINGS.md is that the human faculty for predicting what a code change does to a rendered page is not simulation. It is a memory of rendered scenes, a causal index from code to appearance, a small local imagination applied to a remembered patch, and calibrated doubt about when to go look.

P0 built the index and the imagination for one site and measured them: given a provenance graph that says which regions a token reaches, a frontier model predicts what happens to them 88% of the time exactly and 98% of the time in outcome, with no render and no training. Nobody has shipped this. The nearest work reached 72.9% only by training on the project's own mutations.

P1.3 then qualified that number. It is 88% on synthetic single-token changes. On real commits from the same repository the same system scores 6 to 29% exact, 47 to 71% on outcome, and 72 to 86% field by field. The system gets most fields right and rarely every field of every region, which is what an exact-match metric does to a multi-effect change. Revision 3 splits the goal on exactly that line.

The system is therefore a loop that builds the graph for a site, asks a model what a change does, checks the answer against a real render often enough to stay calibrated, and stops rendering a class of change on the day the calibration says it can. Training is no longer the destination. It is a cost optimisation to be earned.

The difference from the paper is not the model. It is that the graph tells the model where to look. Their model had to find the region; ours is handed it. That is the mechanism behind their 21-point jump from per-project training, computed directly instead of learned.

The gate rule, amended 2026-09-19

A class opened on hot-patch evidence alone would be measuring the easy case. type currently reads OPEN at 96% on hot-patches; on real non-structural commits the best strict number is 45.5% against a 90% threshold.

A class opens only when it clears its bar on real changes as well as synthetic ones. IMPLEMENTED 2026-09-19 in rd/sql/003-gates.sql, and the review of the fix changed it in three ways beyond the original proposal:

Was going toInsteadWhy
add a real-change column, keep "most recent run wins"pool evidence across every clean run, weighted by nmost-recent let an 8-sample smoke test open colour at n=4 over a 32-sample run that said closed. Pooling makes a tiny run unable to move a gate
compare the point estimate to the thresholdcompare the Wilson 95% lower boundat n=25, 96% has a lower bound near 80%. Calling that "cleared 90%" is optimism, not evidence
label real commits with one classscore real commits per effect: colour fields, geometry fieldsa real commit is multi-effect (11 of 17 change all four). Each synthetic class maps to the real effect it manifests as: spacing/type/layout → geometry, colour → colour

Plus: canonical model identity (gpt-6-astra and azure:gpt-6-astra were two rows), thresholds as data in gate_thresholds, a minimum n of 30 on both sides, and a why column that states the exact reason a gate is closed.

Consequence: on all evidence to date, every gate is closed. Not because the real-change rule bit, but because the lower bound bit first: colour pools to lb 0.852 against 0.98, type to 0.853 against 0.90. The synthetic thresholds were set as point estimates; as lower bounds they need roughly n≥60 at 97%+ for type, and colour at 98% needs n in the hundreds. That is the right demand for a mechanism that authorises not rendering, and it is now the plan's stated bar.

Precision and recall do not weigh the same, added 3.1

Measured 2026-09-19 on the 18 held-out real-commit samples, model and floor on identical regions:

true findingsfalse alarmsmissed
trivial predictor77190
claude-opus-565312

Both score F1 near 89, and they are not the same product. Nineteen false alarms in a pull-request comment is a tool people learn to scroll past; three is one they read. A miss, by contrast, costs a regression shipping into a fallback where the render happens anyway and catches it.

So the advisory tier is measured as precision at a stated recall floor, not F1. An unweighted F1 asserts that a false alarm and a miss cost the same, which is a product claim nobody has made. The floor itself is to be set when there is a corpus that can measure it; until then the counts are reported alongside any rate.

This is also the first metric on which a model has clearly beaten the trivial predictor on real commits, 95.6% precision against 80.2%, and it is invisible in the summary statistic.

On hot-patches the model clears the floor by 63 to 70 points of strict. On real commits it is at or below the floor on every metric except astra's strict. The advisory tier's own metrics, relaxed and finding-level, are the ones it loses hardest.

The cause is the corpus. A sample exists because something changed, and here that was almost always geometry: 229 of 281 regions moved, and there is one contrast regression in 281 regions against 216 in 2,103 on the hot-patches, which were built by perturbing colour tokens. A constant "everything moved" is therefore nearly right by construction, and the advisory tier's headline finding has no positives to recall.

So the advisory tier is not reachable-but-unbuilt. It is unmeasured, and this corpus cannot measure it. The claim is withdrawn until GOV.UK, which moves from the next phase to a precondition. Baselines are now recorded beside every run (rd/src/baseline.mjs), flagged is_baseline, and excluded from the calibration the gates read.

What more training could buy, honestly

Three frontier models scored the same on synthetic, 88.0 to three decimals, and collapsed together on real commits. That is the signature of a task ceiling, not a model ceiling: none of them has seen how this site's cascade compounds a multi-file change, and no prompt supplies it. That is the one thing training on real commit pairs can add. The prior art gained 21 points from per-project training, on single-rule mutations, the easy case.

Measured today on real commits: field-level 72% and sample strict 29%; with structure excluded, 86% and 46%. The table reproduces both pairs within noise, so the strict number is mostly arithmetic on the field number. Fields are correlated in practice, which makes the true curve somewhat kinder, but the shape holds.

Amended 3.1: read those field numbers against their floor, not against zero. A constant predictor scores 71.9% field on the same set, and 86.2% with structure excluded. The measured 71.8% and 85.8% are therefore not 72 and 86 points of skill, they are zero. The headroom for training is not "72 to 90", it is "the floor to 90", and the first thing training would have to demonstrate is any lift at all over a predictor that costs nothing.

If P5 runs on real pairs, the plan expects field-level to clear its floor and move toward 90, finding-level precision and recall to clear theirs, and sample strict up 10 to 20 points. No amount of training reaches 88% strict on multi-effect changes: at 98% per field it is 60%. The metric caps the number before the model does. That is why Revision 3 changes the metric and the corpus first, and the weights last.

On a 319-region page a global style change touches far more, so every GOV.UK sample would be filtered out, and the cap cannot simply be raised because 300 regions is 1,500 fields and sample strict on that is arithmetically zero whatever the model does. Regions must be sampled within a page, deterministically, with the sample recorded as a subset. That is the next thing to settle, before any GOV.UK number exists.

What makes it scale

Unchanged from Revision 1: site is a row never a fork; the deploy hook is the distribution channel; the PR comment is the product surface; incremental by default; the residual log compounds. One addition: the frontier model is a shared dependency with a rate ceiling, and the P0 burst test (60 concurrent, zero 429s on astra; 39 of 50 failures on mini at capacity 10) is the number to plan around per deployment.

Where it runs

Everything so far runs on one small shared virtual machine that was already paid for, plus a hosted frontier model. No GPU is used anywhere, and none is available on this account in any region, which is why the plan is built not to need one.

The machine carries the Postgres store. A second inference lane rides a Claude subscription at no cash cost and about four times the latency, which is what makes repeated evaluation affordable. Recording discipline

Added 2026-09-19 after a real loss. An eval loop wrote every model's result to one shared out/p0/eval-hard.json; three of the day's numbers survived only in terminal scrollback and one had to be reconstructed by hand. The rule now:

Source of truththe the project database database: eval_runs (append-only), eval_class_results, phase_log
Raw artefactrd/out/runs/<mode>__<model>[__<class>]__<timestamp>.json, one immutable file per run, never a shared path
Gate tablecalibration, DERIVED by rd_recompute_calibration(). Never written by hand. Only clean (errors = 0) with-distractors runs may open a gate
Human viewdocs/RESULTS.md, generated by python3 scripts/results.py. Safe to overwrite; never edited
Narrativedocs/p0-results-*.md for the story and the caveats. The tables live in the database

Every run records its own caveat in eval_runs.notes. Runs that are superseded or confounded are kept, marked, and excluded from calibration by query, never deleted. Schema: rd/sql/002-results.sql.

Two bugs this discipline caught within an hour of existing: the calibration tiebreak picked arbitrarily among rows sharing a timestamp (fixed with id desc), and record.mjs used execFile's non-existent input option so the DB write silently sent nothing (fixed with spawn). Both would have produced quietly wrong tables.

Verification, the whole plan

  • Layout has a real number, n≥30.
  • Mini has a clean number, n=50.
  • Real-commit strict is within 10 points of hot-patch strict on the same model, or the gap is explained. Explained 2026-09-19: structure is a third, compounding is the rest, and the corpus is one commit. Replaced by the three lines below.
  • Every real-commit run reports per-region exact and finding-level precision/recall, stratified by commit, with counts beside rates.
  • The GOV.UK real-commit corpus reaches n≥200 from ≥40 commits, no commit above a tenth of held-out.
  • Every reported number has a trivial baseline recorded beside it, and beats it.
  • Gate evidence counts each corpus once, and the gate table says how many corpora back it.
  • P5, if it runs, records a win or a kill against zero-shot astra on held-out commits.
  • The same finding shape comes out of GOV.UK.
  • A gate opens on two-site evidence and holds for a week of spot checks.
  • A PR comment lands before the deploy finishes.
  • Astra's cost per thousand findings is on record.

Gates

  • Provisioning anything new on Azure is spend. Nothing is created without a yes. P1 to P4 need nothing new.
  • Raising mini's capacity DONE 2026-09-19, 10 to 100 on the Azure OpenAI account. Quota had 1,980 of 2,000 free; a separate account is a separate account and was not touched.
  • P4 installs a workflow on a public repository and comments on its pull requests.
  • P5 spends Azure credit on a hosted fine-tune. Its own gate, on its own evidence, with the estimate written down before the run.
  • Third-party repos are forked, never touched. GOV.UK is captured from a fork.
  • No credential of any kind lives in a repo.

Not in this plan

  • JavaScript state. Captured where the catalogue reaches it, always rendered, never gated.
  • Cross-browser. Chromium only.
  • A pixel-generating model.
  • Training from scratch. Revision 1's per-site adapters and merge-with-rehearsal stay retired. P5 is one hosted fine-tune on real commit pairs, bounded by one kill criterion.
  • 88% strict on multi-effect real commits. The arithmetic in "What more training could buy" caps it near 60% at 98% per field. The plan does not promise it and the autonomous tier does not depend on it: gates open per class, on lower bounds, or not at all.
  • Reporting any synthetic number without the word synthetic.
  • Reporting any number without its floor. A metric a constant predictor wins is not a result.
  • Discovery at scale before the graph is proven on a second stack.
