Three systems, one seam

The seam between design and code, at three heights

These are not three projects. They are one argument made three times, at different scopes, and the order below is the argument. A design system that a compiler enforces. A process that lets an agent build against it and stops at a person. The plumbing that carries a token from a designer’s hands into a running app. Every link opens something that is actually running.

HeightWhat it settlesWho it is for
The contract What a component is, which tokens exist, and what the system refuses to build. Enforced by a build that fails, not by review. Design systems: the sample below
The process How work gets from an intent to a merged pull request, and where a person has to decide. Fidelity is earned stage by stage. Delivery: the ladder
The plumbing How a token actually travels: a designer changes a value and the running app takes it, before anything merges. Tooling: Sorb

The Figma flow

live · smallest of the three

A designer marks a frame ready for development in Figma. Nobody runs anything. A few minutes later there is a pull request, and a person decides. The interesting part is not the integration, it is the design system underneath it. A pack that is the agent’s entire vocabulary, and a build that refuses a design the system cannot express.

The product The running app, then click Drills …/app/?weak-spot=true · the card is on the Drills tab Click the Drills tab. The page opens on Overview and the card is not there. The link has switched a feature on for your browser and nobody else’s, and it only shows on Drills. Drop the ?weak-spot=true and the card is gone, because that is what everyone else sees. Merged and deployed either way. Merging is not releasing.
The components Storybook eleven components, two brands Two brands are two modes of one variable collection, not two collections. Switch brand and nothing else changes, because there is only one set of names.
The design The Figma file public · five pages Variables for both brands as modes of one collection, and three request frames built only from instances rather than drawn. How this works is the page worth reading. The third frame asks for a chart the system does not have, on purpose.
The contract nhunsaker/figma-design-system-sample public · the whole thing Read design-system/pack.json first. Eleven components, three token tiers, and six refusals, five of which are machine-checked and the sixth says so in the file. Forty nine semantic custom properties per brand and seventy four component ones. Primitives are never emitted at all, so nothing can reach past the semantic layer even if it tries.
Reference What Figma’s APIs can and cannot do the constraints this was built around Written before the code. It says plainly which things are impossible, which is why a webhook has to be translated and why no API can mark a frame ready.

Fidelity Ladder System

live · the process around it

The same seam, one level up. A sentence typed into a web page becomes a written spec, then drawings in a real Figma file, then something clickable, then real code, then a flagged pull request. A person decides every step that cannot be taken back. The subject is a poker app that really exists.

Try it The visitor door harness.n8plusus.com/build/ Type a change and watch it climb. No account, just a name and the shared passcode. Any user name, password gu3st.
What it built The staged app pocket-stage.n8plusus.com/game/rail Every built feature is behind a flag that is off. A merge changes this site. It does not change what a player sees until a person flips the flag. Same rule as the sample above, which is not a coincidence.
The evidence Pull request #26 fls-harness-demo/pull/26 336 lines across 6 files, written as three commits. The project’s own tests re-run against it rather than being believed.
The system nhunsaker/fidelity-ladder-system the open framework · also on PyPI The mechanisms are open. The policy and the running instance are not, which is the split that keeps the framework usable by somebody whose rules differ from mine.

Sorb

live · the plumbing underneath

The layer below both. A Figma-to-React token bridge: a designer’s change previews in the running app before anything merges. Where the sample above proves a design system can be a contract, this is the machinery that carries the values across, as a product rather than a demonstration.

Try it try.sorbcloud.com the guided tour, no account Change a token, watch the running app take it. Two minutes.
On npm @sorb/leaf, the React SDK core 0.3.0 · leaf 0.5.1 · juice 0.3.0 · seed 0.5.1 Four packages, published. Tokens ride as CSS custom properties with fallbacks, so a preview cannot break an app that is not listening.
For agents metatoy/sorb-tap an MCP server for design tokens Point an agent at a DTCG file and it can trace a colour back through its real alias chain instead of guessing. MIT, read-only by design. Not on npm yet. The repo is the thing.
