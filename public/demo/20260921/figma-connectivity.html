REST API

Read almost everything. Write a short, specific list. readwrite
  • Reads: a file and its full node tree, individual nodes, rendered images of nodes at a scale you choose, published components and styles, comments, version history, projects and files in a team, local and published variables, library analytics, dev resources.
  • Writes: comments and replies, dev resources (links attached to a node), webhooks, and variables. Variables writes are Enterprise only, and since November 2025 include extended collections: a child collection that overrides a parent's values, which is the per-brand mechanism for seventeen brands on one system.
  • Cannot: create or move nodes, frames, or components. There is no "draw this" endpoint. Anything that changes the canvas goes through a plugin or the MCP server.
  • Auth: a personal access token for your own account, or OAuth 2 with scopes (file_content:read, file_comments:write, file_variables:read and so on) when the system acts for other people. Rate limits are per token and per plan. Cache the file tree by version id and re-fetch on a webhook rather than on a timer.
  • Where it sits: your server. It is the only Figma surface that runs with nobody logged in, which makes it the read path for everything automated.

Webhooks v2

The only way Figma starts something in your system. trigger
EventFires whenWhat you getUse it for
DEV_MODE_STATUS_UPDATEa layer's Dev Mode status changes, including marked ready for developmentfile key, node id, the new statusthe trigger for a build
LIBRARY_PUBLISHa library is publishedfile key, description, the variables that changedtoken pipeline, pack rebuild, contrast check
FILE_COMMENTa comment is addedfile key, comment text, comment id, mentionsa command channel, and the reply channel
FILE_VERSION_UPDATEa named version is createdfile key, version id, labela deliberate checkpoint, safer than every save
FILE_UPDATEthe file is saved to historyfile key, filename, timestampinvalidate a cache. Too chatty to build on
FILE_DELETEa file is deletedfile key, filenamehousekeeping
  • Scope: a webhook is attached to a team, a project, or a single file. Project and file scope arrived in 2025 and they are the ones to use: a team-wide hook on a hundred-designer org is a firehose.
  • Verify the sender: every delivery carries the passcode you set when you created the hook. Check it before you do anything, the same way you check the HMAC on a GitHub webhook.
  • Assume best effort: deliveries can be delayed, batched, or missed after a burst of saves. Treat the event as a hint, dedupe by file key plus version id, and read the current state with REST before acting. Keep a polling fallback on the version endpoint for the day a hook goes quiet.
  • Needs: the file has to live in a team on a paid plan, and the token that creates the hook needs the webhooks scope.

Plugin API

Full read and write, but only with a person in the file. readwrite
  • JavaScript in a sandbox inside the editor with the whole document in reach: read any node, create frames and components, set variables and styles, bind tokens, export images. FigJam has its own node set (stickies, connectors, shapes) through the same API, and widgets for things that live on the board.
  • Network: a plugin can call your server, but only hosts listed in its manifest. That is how a plugin becomes a trigger: a button in the plugin posts to your API with the selection's node ids.
  • Dev Mode plugins run in the inspect panel and can generate code for the selected node, which is where a design-system-aware codegen lives if you want it inside Figma rather than in the IDE.
  • Cannot run headless. No session, no plugin. Anything you need to happen with nobody in the file has to be REST for reads and the MCP server for writes.
  • Needs: a file open in Figma, and an editor seat for writes. Private plugins need an org or team plan to distribute.

MCP server

The agent's door, both directions. readwrite
  • Two servers: the remote one at mcp.figma.com, reached over OAuth from any MCP client, on every seat and plan. And the local Dev Mode server inside the desktop app, which sees your current selection. The remote one is what a server-side agent uses.
  • Reads: get_design_context (code plus the design-system components and variables behind a node), get_screenshot, get_metadata (the tree, cheaply), get_variable_defs, get_code_connect_map, search_design_system, and get_figjam for boards.
  • Writes, since February 2026: use_figma runs Plugin API JavaScript against the file, so an agent can create frames, components, variables and auto layout that are real Figma structure, not pictures. generate_figma_design captures a web page into a frame, generate_diagram draws Mermaid into FigJam, create_new_file starts a file, and assets upload and download.
  • Needs: any seat to read. A Full seat to write. A Dev seat is read only. Writes happen as that seat, in that file, visibly in version history, which is the audit trail you want anyway.
  • In the diagram this is the MCP layer: the tools the agent calls and the surface a designer prompts through. One layer, two users.

Code Connect

The binding between a Figma component and the code component. readwrite
  • A file in the repo, per component, that says which Figma component it is and how its props map. The CLI publishes the mapping to Figma. Dev Mode and the MCP server then show real code for a frame instead of a guess.
  • Supports React, SwiftUI, Compose and HTML style targets. For a Cocos runtime the same idea applies through a custom mapping in the pack, since Code Connect will not know the engine.
  • Why it matters here: it is the mechanism behind the diagram's line "a frame names a component that exists." Without it, the contract is a document. With it, the contract is a lookup.

Dev Mode and the apps

Where designers and developers already meet, and where status lives. readwritetrigger
  • Ready for development is a status on a layer, set by a person. It is both the human handoff and the machine trigger, because the webhook fires on it.
  • Dev resources are links pinned to a node: a Storybook story, a Jira ticket, a GitHub PR, a stage URL. Writable by REST, so the system can pin the pull request to the frame it came from.
  • The Jira app attaches designs to issues and mirrors status. the GitHub app shows design previews on pull requests. Storybook embeds live stories next to the frame. None of these is a build mechanism. All of them are how the loop closes for a person.
  • The VS Code extension puts Dev Mode in the editor. Useful for a developer. Not part of the automated path.

Variables and tokens

The one layer where the plan you are on decides the architecture.
  • Every plan: a plugin can read and write variables in the open file, and can export them as DTCG JSON. That is enough for a pipeline that a designer runs on purpose.
  • Enterprise: the REST variables endpoints read and write without a session, and extended collections give you a parent system with per-brand overrides while keeping one source of truth. This is the seventeen-brand answer, and it is gated by plan.
  • The publish event is the same on both: LIBRARY_PUBLISH tells you the tokens changed, with the variables in the payload. Compile per runtime from there: CSS custom properties for the web codebases, engine values for Cocos.
  • Direction of truth: decide it once. Either Figma variables are the source and the repo compiles from them, or a token file in the repo is the source and a plugin pushes to Figma. Both work. Two sources do not.

What will bite

The constraints that shape the design, in the order they usually come up.
  • Nothing draws without a session. REST cannot create a frame. The plugin needs a person. The MCP server writes as a seat. So "the agent writes wireframes" always means a Full seat that the agent acts as, and that seat's name is on the version history.
  • Variables writes are Enterprise only. If the org is not, the token pipeline runs through a plugin a designer triggers, or the repo is the source of truth and Figma is a mirror.
  • Webhooks are hints. Delayed, sometimes batched, occasionally missed. Verify the passcode, dedupe on version id, read the real state with REST, and keep a poll on the version endpoint.
  • File-scoped hooks or nothing. A team-scoped hook on a hundred designers is a firehose with no filter.
  • Rate limits are per token and per plan. Cache the tree by version id. Re-read on events, not on a timer.
  • Tokens are secrets. A personal access token reads every file its owner can see. The agent's token lives in the server's secret store, never in the worktree the agent runs in, which is the diagram's "no secrets" line.
