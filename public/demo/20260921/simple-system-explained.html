Reference · the sample system, area by area

The simple system, explained

A designer marks a frame ready. One small service reads it and opens a request. An agent builds against a schema, checks refuse what the schema forbids, a person approves, and the result is pinned back onto the frame. Everything below is that sentence, taken one area at a time.

Every figure here was measured on the running system, not estimated. Where something is a design rather than a thing that has been run, it says so in a red block. Vocabulary throughout: spec, wireframe, preview, build, ship.

Figma and the design system

The file is the trigger and the reference. It is not the source of truth for values.

The Figma file has five pages: a cover, how this works, foundations, components, and requests. The foundations page holds variables for two brands, Harbor and Ember, as two modes of one collection rather than two collections. The components page holds the components as real Figma components with variants. The requests page holds three frames built only from instances of those components, never drawn by hand, and one of them deliberately asks for a component the system does not have.

Where truth lives

The source of truth for token values is four JSON files in the repository: primitives, component-tier tokens, and one semantic file per brand. The build reads only those and makes zero calls to Figma. The Figma variables are a copy made once to match. If the file were deleted the repository would compile identically.

This is stated rather than buried because it decides who wins when the two disagree, and the honest answer today is the repository, silently. At one designer and one developer that is fine. At seventeen brands it is the first thing to fix, and the fix is a plugin that pushes the repository's tokens into Figma, because REST cannot write variables below the Enterprise plan.

The trap next to that: the published-components endpoint returns an empty list with a 200 on an unpublished file, which looks exactly like a file with nothing in it.

The component library

Twelve components, three token tiers, and a build that refuses a design the system cannot express.

The library is small on purpose: DesignSystem, Button, Badge, Card, Input, Tabs, Toast, Stack, Stat, Meter, RecordRow, and Missing. Each lives in src/components with a stylesheet, stories and tests, and each has an entry in the pack naming its purpose, its props and its Figma counterpart. Underneath sits a vendor library, wired through runtime custom properties so a brand change re-skins it without a rebuild. The vendor may be imported in that one directory and nowhere else, which is checked.

Three tiers, and the tier rule is enforced by the compiler

TierMay referenceEmitted asCount
Primitivenothing, literals onlynever emitted93 in source
Semanticprimitives onlycustom properties, one block per brand49 per brand

Primitives are never emitted as custom properties. So nothing downstream can reach past the semantic layer, not because a rule says so but because the names do not exist in the output. A grep of the brand stylesheet for a primitive name returns zero, and that is the proof rather than the policy.

The contrast gate

Sixteen colour pairings are declared in the pack, twelve for text and four for structure. The build computes each from every brand at compile time, thirty two checks per build, and refuses to compile a brand that fails its floor: 4.5 to 1 for text, 3 to 1 for structure. An illegal palette is a broken build rather than an accessibility finding six months later. It caught its author: a border colour at 2.52 to 1 against white in both brands, not found in review, found by the build naming the token and the ratio.

Missing, the twelfth component

A placeholder for any component the pack cannot build. It reserves the exact footprint the design allotted, names the component, says why it is not there, and carries the full sentence as its accessible name. It is a real member of the pack, which is what lets the contract check accept it. It asserts nothing about why a component is missing, which is the point: an unmapped instance is equally a new component, a new variant of an existing one, an instance from another library, or a rename. A placeholder is true in every case, so no classifier is needed.

AI tooling and agents

The agent is not asked to write good code. It is asked to satisfy a schema, and the schema is the design system.

The coding agent is GitHub's, assigned to the issue by the translating service. No model credential lives in the repository. The agent runs on GitHub with its own per-run token, minted by GitHub and scoped to that run, and holds no design credential of any kind. It sees what the issue carries and nothing more.

What the issue carries

  • An idempotency marker in the body, so a redelivered webhook finds the first issue instead of opening a second. No database.
  • A link to the frame and a temporary image of it.
  • What the frame is made of: mapped components by pack name, unmapped ones by their Figma name with their measured size.
  • How the frame is arranged: an outline in document order. Instances are opaque, a laid-out frame becomes a level and says which way it runs, a plain group is transparent, and three identical siblings collapse to one line.
  • The words in the frame, to be used exactly, because copy is a design decision. Text inside an unmapped component is excluded, because it belongs to something that will not be built.
  • Acceptance: matches the frame, only pack components, a story, tests pass, behind a flag set to false.
  • For an unmapped component: use Missing with the name and size, build the rest normally, say so under Left undone.
The arrangement outline exists because of a real run. The first two runs put a placeholder above the figures the design puts below them, and nothing in the issue said otherwise. The component list was a sorted set, so every trace of position was thrown away before the issue was written. The tree was already walked in order; the ordering was being discarded.

What happens on a miss

The third request frame asks for a chart the pack does not have. On the first run the agent built the heading and the figures and left a hole with a stray line of orphaned copy. On the second, told to use the placeholder and given the size, it wrote <Missing name="Sparkline" width={672} height={80} /> and explained it under Left undone. Naming a sanctioned way to comply changed what it did. That is the finding, and it came from running it.

Production frontend code

Merging is not releasing. Every change lands with its flag off.

The application is a small React page built entirely from pack components, deployed to GitHub Pages from main alongside Storybook. Every change an agent lands arrives behind a flag in src/flags.ts set to false, in every environment. A merge moves code without shipping a feature. One query parameter turns a feature on for one browser and nobody else, so a reviewer can see a change live without anyone else seeing it.

What a merged change looks like

A branch, a draft pull request with a body that fills five required sections, a flag that exists and is off, a story for the new state, tests for flag-off and flag-on, and the project's own checks re-run against it rather than believed. On merge, the pull request is pinned back onto the frame as a dev resource, and a comment says the change is behind a flag that is off, so nothing has changed for anyone yet.

What the pipeline cannot carry. The contract can only express what a designer built as an instance. A container drawn as a styled frame rather than a Card instance is invisible to the bridge, so the agent gets the image and no structured signal that a surface was wanted. The fix is not code. It is a rule for the design file: containers are Card instances, rows are Stack instances. The same discipline the code side already enforces, applied to the Figma side.

Architecture

Three boxes, and only the middle one holds a key.
DESIGN THE TRANSLATOR WHERE CODE LIVES a frame marked ready ──▶ reads the frame ──▶ issue, labelled and assigned opens the request agent builds on a branch holds the only Figma key checks refuse what the pack forbids a person approves frame gets the link ◀── pins it back ◀── merged, flag off, Pages deploys the pack governs every stage: the vocabulary the agent may use and the schema the checks judge against

The translator, and why it exists at all

A Figma webhook can post to an address and cannot set an Authorization header. GitHub will not accept a write without one. So something has to receive the first and issue the second. That is the entire job. It is stateless, with no database, cache or session. Idempotency rides on a marker in the issue body. It has three routes: a health check and two one-way doors that only two specific senders may use.

It is not an API. Nobody queries it and it returns nothing to anyone. It is a webhook-to-API translator, which is what the directory is called, and naming it that makes someone ask why translation is necessary, which has a one-sentence answer.

It exists twice, held to one spec

A Python service for a machine you control, where every credential stays in the operating system keychain. And a Cloudflare Worker with nothing to operate, where the credentials leave your machine for a third party's configuration. Both are held to contract/: a behaviour table of thirteen cases, and golden files for the issue body diffed byte for byte in both suites, because the body is the entire contract with the agent and two wordings would be two behaviours. Changing one word in one runtime fails tests in both.

Guardrails

Structural, not prompted. If you are prompting the guardrails at the agent, the fox is in the henhouse.

The pack names six refusals and, for each, which check enforces it. Five are machine-checked. The sixth says so.

RefusalEnforced byWhat it refuses
raw-valuecontract checkAny hex, rgb or hsl colour, any px, rem or em length, any duration, in a stylesheet or styled block. Any var(--ds-*) the pack does not declare
outside-packcontract checkThe vendor imported outside its one directory. Anything in src/components the pack does not list. A component stylesheet anywhere else. A pack component with no story or no test
accent-spreadcontract checkThe accent used directly rather than through a component token
brand-forkthe buildA brand that sets a component-tier token, or omits a semantic one another brand declares
motion-unguardedcontract checkAn animation with no reduced-motion guard
colour-alonereviewA state carried by colour alone. Needs a person, and the pack says so rather than pretending

The gates a person holds

  • Before an agent's code runs at all. GitHub holds workflow runs on bot-authored pull requests until someone with write access approves them. Without that, an agent that can write to the workflows directory could author one and have it execute.
  • Before anything merges. Branch protection requires three checks and one approving review. Workflow permissions are read-only and Actions cannot approve reviews, so an agent's run cannot approve its own work.
  • Before anything ships. The flag. Turning it on is a separate act, by a person, outside the pipeline.
The fence is not a wall, and the pack says so. The contract check stops the accident and the shortcut. Somebody determined could still style a component in the page shell. That is the right amount of enforcement for a design system, because the alternative is a build nobody can work in, and the token rules still apply to every line of that stylesheet.

Validation

A check that did not run is never reported as one that passed.

Three checks, each owning a different file, wired so a pull request cannot merge unless all three pass and a person approves.

The build checks the token files

Tier direction, brand parity, name collisions, accent purity, the contrast floor, dangling references and cycles. In CI it runs with --check, which fails if the committed generated output differs from what the source produces. A stale pack is a failed build.

The contract check checks the source against the pack

Every refusal in the table above. It exits 0 for pass, 1 when the code is wrong, and 2 when the check could not run. CI fails on both 1 and 2. That last rule is the one to say out loud.

The pull request check checks the body

Five required sections, a frame link that names a node, a flag that exists in the flag module, and a Left undone that says something. It reads the body live from the API at the moment it runs rather than from the event snapshot, because an agent opens a draft with a work-in-progress checklist and writes the real description later. Drafts are exempt, because a draft is a statement that the work is not finished.

The tests, and what they are for

SuiteCountWhat it proves

What green tests did not catch, three times. A deployed Worker that threw on every real webhook, because every test injected a fake fetch and the default was never exercised, and the failure only exists on the real edge. Every component in the deployed Storybook rendering unstyled, because the component tier was declared on the root and the brand class sat on a div, and no check looked at selectors. And a placeholder above the figures the design puts below, because the issue described contents and never composition. Each was found by looking at the running thing. The decisions file already said so.

The visual check is advisory

A story screenshot compared against the Figma export, commenting on the pull request rather than blocking it, until its false-positive rate on real pull requests earns otherwise. Unbuilt, and named as such.

Operating model

One human gate, not five. Gates are how you give people more autonomy, not less.

Who does what

PersonDoesNever does
DesignerMarks a frame ready. Iterates on the prototype and marks it ready again. Sets a frame to completedRuns anything. Touches code
DeveloperApproves the workflow run, reviews the pull request, approves or requests changes, turns a flag onMerges an agent's work without reading it. Edits the design system to make a request fit
The agentBuilds on a branch against the pack, opens a draft, says what it left undoneTouches the design system or the checks. Merges. Holds a design credential
The serviceTranslates one event into one request and writes the outcome backDecides anything

Why one gate

A wrong direction is discovered at the pull request, the most expensive place to discover it. That is accepted because tasks are small, scoped to one frame, with the design attached to the issue, so a wrong direction is cheap to throw away. More gates would be building the interesting system rather than the smallest one that works. The evidence for more gates exists elsewhere: across five clean runs, twenty seven seeds and three products, roughly one in ten agent steps advanced in a wrong direction, and thirteen of fourteen deliberately wrong directions were caught at or before the step where they were knowable. The labels were a second pass by one author, not an independent co-labeller.

The one decision that makes it staffable

Designers review the prototype and revise it before a developer sees it, so handoff becomes closer to a code review. The scarce resource was never the model. It was developer attention.

IfDev reviews a dayDev reviewers needed
Developers absorb two to three rounds~12,000250
Designers iterate, developers see one round4,800100
Designers iterate and only promote some~1,60033

This spends tokens to buy back attention, and tokens are three orders of magnitude cheaper. It creates two requirements: a preview per run a designer can open without a developer, and revision as something a designer can trigger. The frame is the input, so revising the frame and marking it ready again is the loop.

What a miss means for the organisation

A component the system cannot build produces a visible, labelled placeholder and a named gap. Needing it often is a request to grow the system, not a reason to work around it. That is the difference between a design system and a suggestion, and it is worth saying out loud.

Many brands from one system

Brands are modes of one collection, not seventeen collections. There is only one set of names.

How the simple system knows a brand

A brand is one semantic token file. Harbor and Ember each declare the same 49 names with their own values, and the build refuses to compile if their key sets differ by even one. The generated stylesheet has one block per brand, .brand-harbor and .brand-ember, each redefining the same custom properties. Selecting a brand is putting one class on the root element. Nothing else changes, because there is nothing else to change.

Of the 49 semantic tokens, 17 differ between the two brands. The other 32 are shared: spacing, radii, type scale, line heights, motion. That ratio is the honest measure of how different two brands actually are, and it is usually smaller than the brand teams believe.

How a brand cannot fork a component

The component tier is compiled once for every brand, because every value in it is a reference into the semantic tier and never a literal. A brand file that tries to set a component-tier token fails the build with a named error. So Button's padding, radius and colours resolve from whatever the brand says the semantic values are, and no brand can give Button a different shape. That is the proof that seventeen brands stay one system: the component tier is one file and the build will not let a brand touch it.

Where the component tier is declared decides whether nesting works. A custom property resolves where it is declared. Declared on the root, the component tier resolved once against whatever brand was on the root and inherited that everywhere, so a nested brand switch changed the semantic tokens and left every component token on the outer brand's values. Declared on the brand selectors instead, a nested .brand-ember inside a Harbor page now correctly turns the primary button purple. Found on the deployed Storybook, where every component rendered unstyled; fixed; and a check now fails if either dependent tier goes back to the root.

Per-brand guarantees

  • The contrast floor is computed per brand. Sixteen pairings, thirty two checks. A brand whose palette fails one does not compile.
  • The accent may not equal any status colour, per brand, so a warning can never look like an action.
  • A brand that omits a token another brand declares fails parity. Every brand answers every question.

Scaling from two to seventeen

Adding a brand is adding one semantic file and one line in the build's brand list. Nothing in the component tier, the components, the checks, the bridge or the agent changes, because none of them know how many brands there are. What does change is the shape of the brand question: at seventeen, most will be palettes over a shared structure, and the parity rule will surface which ones are genuinely different. Figma's answer at that scale is variable modes or, on Enterprise, extended collections with a parent system and per-brand overrides. The repository's answer is the same file layout, seventeen deep.

Not yet built: a check that the pack's declared props match the code. Add a variant in code without updating the pack and the build stays green, so the agent is told a narrower vocabulary than exists. Named as the next thing to close.

Cocos as an output, versus the web

Tokens are values, not CSS. The pack names components and rules, not implementations. Both survive the crossing. The cascade does not.
This section is design, not evidence. The sample targets the web. Nothing here has been run against Cocos Creator. What follows is what transfers, what does not, and what would have to be built, stated so it can be checked rather than believed.

What Cocos is, for this purpose

Cocos Creator is a TypeScript game engine with its own scene graph and UI nodes. There is no DOM, no stylesheet and no cascade. Colour is a value on a node, spacing is a number on a layout component, type is a font asset and a size. Some teams run Cocos with web components inside it, which means two paths exist side by side: native Cocos UI, and web-rendered surfaces embedded in it.

The one real difference: no cascade

On the web, a component token is a var() that resolves at use time against whatever brand class is above it in the tree. A nested brand works because inheritance does it for free. Cocos has no inheritance of that kind. A colour is set on a node and stays set. So on Cocos the component tier is resolved at generation time: the emitter produces, per brand, a module where every component token is already a concrete value. Switching brand is swapping which module is loaded, or reading from a brand-keyed table at runtime. Nested brands do not exist as a concept, which is fine, because a game screen is one brand.

Everything the web gets from the cascade for free, Cocos gets from the generator instead. That is more code in the build and less magic at runtime, and for a game engine that is the right trade.

The web components inside Cocos

Those are the easy path. They are web surfaces, so they take the same CSS custom properties the rest of the web does, with the brand class on their root. The only question is which brand class, and the Cocos host knows, because it loaded that brand's module. One system, two emitters, and the embedded web surfaces are simply the first emitter used from inside the second.

What the agent would be told

The issue does not change. It names components by pack name and words by copy, neither of which is runtime-specific. What changes is the pack's import field for each component and the acceptance line, which would name the Cocos test command instead of the web one. The agent reads the pack and builds against whichever runtime that pack describes. A frame does not know or care whether it becomes React or a Cocos prefab.

What would have to be built, in order

  1. A Cocos emitter in the build: semantic tier as typed constants per brand, component tier resolved. A day.
  2. A Cocos version of the contract check: literal colours and lengths where a token exists, components outside the pack. The refusal ids are the same. Two days.
  3. Twelve components as prefabs or scripts, with the same names and props the pack declares. This is the real cost and it is the same cost any second runtime pays.
  4. A second import path per component in the pack, and a runtime field on the request so the bridge knows which acceptance line to write.
The one-line version. The design system is a contract about names, values and rules. The web and Cocos are two things that satisfy it. Nothing that makes seventeen brands one system depends on CSS, which is why the same seventeen files serve both.
