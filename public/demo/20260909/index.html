2015–2019 · Chapter 1

The platform, on the internal style framework

PubHub is BuzzFeed's social-publishing platform: 100+ connected channels, 40+ editors, hundreds of posts a day across six networks and fifteen post types. I joined in 2015 and owned its frontend for the rest of its life: a React app that grew to ~160 components and ~70k lines (composer, planner, settings, automations, an SDK) on a Python/Tornado backend, deployed through the company PaaS.

It was built on Solid, BuzzFeed's internal style framework. Solid was under-supported, every team re-solved the same UI problems, and Figma-to-code was a manual handoff: designers designed freely, engineers re-implemented by eye. The platform worked (95% user satisfaction in its health checks) but every feature paid a tax to the foundation it stood on.

2020–2022 · Chapter 2

Solid → Bootstrap → Foundation UI: a design system that held

In 2020 I led PubHub off Solid onto Bootstrap with two other developers: a boring base on purpose, so design effort could go to our patterns, our form conventions, and our review rubric instead of re-solving solved problems. We were the first team to break away; internal tools org-wide moved off Solid afterward because the replacement was visibly better to build on, not by decree.

On that foundation I implemented Foundation UI (2021–2022), our product designer's redesign of the post-creation surfaces, as a reusable toolkit of standardized inputs and page patterns. The design was hers; the foundation choice and the build were mine. It re-foundationed an eight-year-old production tool in flight and stayed the team's working standard for the rest of the platform's life with no rewrite. When new draft types arrived (TikTok video, Reels, Instagram carousels) they shipped quickly because the toolkit existed.

How it was governed without a council

  • Kitchen-sink first: every component developed, tested, and merged on a kitchen-sink page before touching a real screen; a weekly cadence of shippable pieces.
  • Feature-flag rollout, phased by platform: Facebook Video first, then the rest.
  • The rubric written down: the team's design principles as the explicit review criteria, RFCs with comment periods for significant changes, scaffolded components with tests, Storybook stories, and README by default, so peer review could carry quality.
  • Adoption: the R&R team (6 developers), about four other internal-tools teams, three designers; shared FUI packages consumed across internal projects; the company React component library at 79 consumers.
The honest cost of a versioned library: shipping a shared-component change meant a version bump, a publish, then updating and deploying each consuming service just to test it, sometimes three services for one change. Living that loop for years is why I later built Sorb (coda), and why, when the migration came, the design system was treated as fixed.

2025–2026 · Chapter 3 · the deep dive

The migration, with AI: the rewrite nobody had time for

By 2025 the backend's age had put a multi-quarter manual rewrite on the roadmap for years, and the team never had the capacity to start it. The idea was narrower than "use AI on the codebase": a behavior-matched Next.js port, one slice at a time, with the existing test suite as the contract, the running production app as the oracle, the design system held fixed, and me deciding only where judgment was actually required. If it worked once it would be a method, not a project.

Spec first, with a number on it

I did not point an AI at the repo and hope. The design was a written spec: the goal, the port mechanics for each legacy piece, the order of slices, and the rules for when the agent must stop. Thirteen tasks against the team's sixty-one-hour estimate, so there was a clock to beat and a definition of done before any code moved. The prototype was the first slice (scaffold, mount, SSO, the API-gateway and image-builder proxies, SSR bootstrap state), rendered side by side with production until it matched.

Make the tests trustworthy before touching the framework

At 26% line coverage the suite could not serve as a contract, so worker agents raised it first: 26% → 97%, about 2,081 generated tests (suite 184 → ~2,265), which surfaced four real latent bugs before a single page moved. Thresholds were locked so coverage could not silently regress.

The agent loop, gated by a human at every consequential decision

The agent worked the plan in small slices, ran the full suite plus lint on every commit, and verified each migrated page against production. It ran free on the typing and stopped at every consequential decision: a data-model shape, a proxy edge case, a behavior that did not match. 71 of those, each logged with the choice and the reason. Chrome DevTools was a hard prerequisite so the agent inspected the running UI itself. Every wall (a build quirk, an SSR gotcha) became a written-down answer. It ran overnight; I decided in the morning.

Result

Nine hundred files, seventy thousand lines, behavior-matched to the original and validated on stage, merged behind flags, in about 8% of the estimate: about five human hours, tracked on a separate clock from the wall-clock hours the loop ran unattended. Then generalized into a reusable blueprint (the agent persona, the decision defaults, the library of answers) queued for about a dozen similar services.

2026 · Chapter 4

What the modern stack unlocked: agentic feature work on a platform that could finally move

Once PubHub was on Next.js the team could iterate on core features agentically, the same loop applied to new work instead of a port. Two shipped; two were in flight when the July 2026 layoffs ended the run.

The AI-native explorations on the same platform

  • Support triage agent (production beta): PubHub's support load was about one in seven team hours. I spearheaded an agent that classifies, investigates the live system, and drafts the fix and reply, with a person approving every action: 84% handling accuracy on a golden set of resolved tickets it had never seen, routing raised from 54% to the mid-70s on a locked holdout, a two-key fail-closed write policy, a team-wide month-long production beta.
  • Nudge recommendations (in flight): a feature-recommendation system for the recommendation queue; proven, not fully implemented at departure.

After BuzzFeed · Coda

Where the pattern went next: Sorb, at the design seam (studio, solo)

The versioned-library loop from chapter 2 and the verify-against-the-running-app rule from chapter 3 became a product. A designer edits a token in Figma, the plugin posts it to a bridge, and the React SDK applies it as CSS custom properties so the real components re-skin live before anyone merges. Tokens modeled primitive → semantic → component; adapters for six UI frameworks; every AI feature proposes, the live app confirms, a person merges. Solo work, said as such; the team-scale evidence is the four chapters above.

How the arc maps to your six steps

  • Idea: chapter 3, the narrow idea of a behavior-matched port as a method; chapter 1 is what existed.
  • Design / prototype: the written spec with a number on it and the first slice rendered against production (ch. 3); kitchen-sink-first components (ch. 2).
  • Design system: chapter 2, Foundation UI, held fixed as the migration's constraint.
  • Code: the agent loop, 71 human-gated decisions (ch. 3).
  • Validation: coverage 26 → 97% first, suite green per commit, side-by-side with production, stage (ch. 3); health checks and A/B on the platform (ch. 1–2); golden-set evals on the triage agent (ch. 4).
  • Production: merged behind flags, blueprint for twelve services, features shipped on the new stack (ch. 3–4).

Honest limits

  • The blueprint was queued across twelve services, not yet applied to them, when the layoffs hit; Nudge and the full triage rollout were in flight.
  • The migration was a behavior-matched port: the design system was preserved, not generated, by the agent.
  • Figma Code Connect was evaluated with our VP of Technology and design leadership, not shipped; that gap is what Sorb was built to close.
