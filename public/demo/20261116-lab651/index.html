Did well

Failed

Dropped two config values that only exist at deploy time (three publish failures, one cause), and skipped a whole class of legacy redirect handler.

Caught by

The full suite after every slice, stage validation of every route and API write (2,306 passing), and a watched production window. One fix for the config gap; two more redirects found before users hit them.

Support triage agent

BuzzFeed · the project behind "Automate the Queue" at the Applied AI Conference

54% → 83.5%accuracy on held-out tickets
20 hrsa week returned to the team
100%of actions approved by a person in beta

Did well

Trained the rulebook in cycles (sample, blind triage, score against what really happened, revise), then drafted investigations and replies in minutes.

Failed

One ticket looped about 11 passes. A race left the agent running with tools missing. A richer routing guide improved routing but dropped overall accuracy to 72.8%.

Caught by

Scoring against real outcomes, never an LLM judge. A locked held-out set. Caps on turns and write calls. Every approval stored, which doubles as an audit trail and training labels.

Current work: an eval plan for agents that build components

Enterprise design system, client not named. Plan approved, harness in progress, no results yet.

Coding agents get a design system to read through an MCP server and learn to turn component contracts into real components. Their output tends to look right while misusing the system: invented token values, props that don't exist, the wrong version. The eval plan turns "reproducible" and "conformant" into numbers, and flags any prompt, skill or model change that makes things worse.

1 · Tool accuracyCall the MCP tools directly, no model. Right lists, right contracts, right "not found". Free and deterministic, on every change.
2 · Agent with MCPA headless agent answers real questions, each aimed at a known failure. Costs credits, so it runs before releases.
3 · GenerationThe agent writes a contract or a component and is scored against an answer key. Most expensive, so nightly or manual.

How one generation case runs

  1. Copy the repo into a sandbox with the answer files removed.
  2. Install the skill under test and the MCP server.
  3. Run the agent headless. Record transcript, files, time and tokens.
  4. If it read a removed file, the case fails automatically.
  5. Graders score the output, three runs per case.

Scored deterministically first

  • Valid against the schema, nothing invented.
  • Builds, lints, and passes hidden tests written from the contract.
  • Only approved tokens; zero serious accessibility issues.
  • Round trip: re-extracting the code gives back the contract.
  • An LLM judge only for prose, and only if it agrees with two human raters.

Rollout starts by testing the tests: a fake perfect agent must pass every check and a planted broken one must fail for the right reasons before any model run. Thresholds come from a baseline, not guesses. Built on promptfoo, run locally and in CI, so client code never leaves the network.

One record, three uses

How my studio, Metatoy, keeps track of its agents.

Every agent run in the studio leaves a record: the prompt, the context it pulled in, the model, what it changed and the tokens it used. That one record does three jobs.

1 · Better contextThe records are indexed for retrieval (RAG). Before a new task, the agent pulls in the past prompts, decisions and fixes that apply, so it starts from what already worked.
2 · Audit trailThe same record answers who asked for what, what the agent saw and what it changed. Add the approver and make it append-only, and it becomes an audit log.
3 · Cost and tuningToken use per run and per workflow shows which steps cost the most and which are worth it, so I tune the workflow with numbers instead of guesses.

For regulated work an audit log needs more: append-only storage, trusted time stamps, signatures bound to the record, and pinned model versions. The shape of the record stays the same.

Rules I hold on AI-written code

A person owns every merge.Agents draft. I review every line and answer for it.
Deterministic checks decide pass or fail.Model-judged evals come after, never instead.
Every requirement traces to a test.Generated from the work, not kept by hand.
Pin model and tool versions.Treat them like any other validated configuration.
A wrong spec gets built perfectly.So the spec gets the hardest review of all.
Agents skip things confidently.The checks are built in, not left to memory.

On regulated work: I haven't owned a formal IEC 62304 or Part 11 submission. I have consulted for regulated clients and built the controls those standards ask for: approval gates, audit trails, change control and traceability from requirement to test.
