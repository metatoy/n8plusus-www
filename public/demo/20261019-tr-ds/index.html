Design systems an agent can read

Coding agents produce output that looks right and misuses the design system: a token value that doesn't exist, a prop the component never had, the wrong component, an answer that was true two versions ago. This is the work I'm doing on that problem now, for an enterprise design system: a read-only MCP server, the component contracts it serves, and an eval plan that measures whether any of it helps. Then the stack, and the delivery system I run my own projects on.

1. The problem, and the layers that fix it

current work

Today the component code, the Figma library, Storybook and the docs each describe the same components separately, and people keep them in sync by hand. The program turns the design system into structured data, so every output is generated from one source and AI tools read that source instead of guessing.

TokensThe values. Three tiers, primitive → semantic → component, defined once, validated against a schema, synced from Figma, published as token-only packages.
Component contractsThe parameters. One JSON document per component: props, variants, slots, states, behavior, accessibility, token bindings, usage. The single source of truth.
GenerationComponent scaffolds (and later Figma output) generated from contracts by AI skills, with conformance checks that measure drift between contract, code and Figma.
MCP serverGives coding agents authoritative component and token information, correct for the version installed in the project they're working in.
ConstraintsOne framework this quarter. Read-only: no write paths in the server. A code freeze in mid-December. Anything hosted needs a security review, so the first release isn't hosted.

2. The MCP server

TypeScript · SDK v2 · stdio

A versioned npm package the developer's agent host (Kiro, Claude Code, Cursor) launches locally over stdio. No port, no URL, no infrastructure, and nothing to put through a network security review. The same server object can be handed to a Streamable HTTP transport later, when a consumer genuinely can't run a local process.

Tools
list_componentsget_contractfind_componenthealth
All read-only. Contracts are also candidates to expose as MCP resources.
DataContracts ship inside the component library's own package, so they're versioned with the components they describe. The server never bundles its own copy.
VersionThe server resolves the consuming project's installed library with Node's resolver (a --project flag, then an environment variable, then the working directory), reads that version's contracts, and echoes the version in every response.
FailureLoud and specific. No library found: every tool returns an error that lists the paths searched and the flag that fixes it. Unknown component: an error that lists the real names, never a "close" match.
Loggingstderr only (stdout carries the protocol), one logging module, tool failures as structured results, field-level validation errors.
AdoptionAn init command that writes the agent host's MCP config and the dev dependency, safely re-runnable; a tagged release job; a docs page; one line in the agent's steering file.
developer's repo └─ agent host (Kiro / Claude Code / Cursor) └─ spawns: mcp server ── stdio ── tools: list / get / find └─ resolves THIS project's installed library └─ contracts/*.json (same version as the components)

Definition of done for the first release: a developer runs init, opens their agent, and it can list components, fetch a contract that matches the installed version, and get a clear "not found" or "library not installed here" when that's the truth.

3. Contracts and the schema

JSON Schema · draft-07

Hand-authored contracts drift and miss things. Writing them is a pipeline: deterministic first, model second, a person for intent.

1. ExtractA script reads the component source and records the facts code can prove: inputs, outputs, selectors, slots, token use.
2. DraftAn agent skill drafts the contract from those facts, and asks a person for what code can't say: usage guidance, accessibility intent, anatomy.
3. ValidateThe contract is checked against the JSON Schema. TypeScript types are generated from the schema, never written by hand.
4. EvolveOnce every component has a contract, the next schema version is derived from what the contracts actually contain, not designed in the abstract.
Schema shapeA platform-neutral core (props, variants, states, slots, a11y, token bindings) plus a block per platform and framework version, so one contract can describe the same component in more than one framework.

4. The promptfoo eval plan

local only · CI

Without a repeatable score, nobody can tell whether a new skill, prompt or model made the agent better or just different. promptfoo: MIT licensed, Node, YAML configs, runs locally and in CI, repeats runs to expose non-determinism, and wraps any CLI agent as a provider. Braintrust was ruled out for now because it's SaaS, so client code would leave the network. Telemetry off, no cloud sharing; results stay in CI artifacts.

Three levels, cheapest first

1. Tool accuracyEach MCP tool returns the right data: lists, contracts, search hits, not-found, version echo. No model involved, so it's free and deterministic. Runs on every change.
2. Agent + MCPA headless agent with the server connected answers real questions. Each question targets a known failure: invented token values, wrong props, the wrong component, the wrong version. Runs before releases.
3. GenerationAgent-written contracts and components, scored against gold answers. The most expensive level, run nightly or by hand, never on every merge request.

How a generation case runs

case ── sandbox git worktree (answer files removed) ── install the skill under test + the MCP server ── run the agent headless; capture transcript, files, time, tokens ── contamination check: did it read a held-out file? → fail ── graders

Graders: deterministic before judged

An LLM judge is used only for prose (usage text, descriptions), and only after it agrees with two human raters on the baseline. If it doesn't, it's dropped. Round-trip conformance re-runs the extractor on the generated code and diffs it against the contract, which doubles as the contract-to-code drift check.

Phases

0. InventoryPick the baseline components, confirm the new ones, confirm the agent runs headless with the server, get the CI secret approved.
1. Self-testA fake "perfect" provider must pass every grader and a "broken" one must fail for the planted reasons, before any model run.
2–3. BaselinesRegenerate components that already exist, where the real code and reviewed contracts are the answer key. Each case runs three times; report pass rate and pass-all-three.
4. CalibrateSet thresholds from the baseline, not guesses. Check the judge against people.
5. New workThree new form controls from the roadmap. Gold contracts and hidden tests are written first (roving tabindex, indeterminate state, bounds), then the runs, then human review.
6. CIManual and nightly jobs with a regression diff against the last committed baseline.

Cost is planned, not discovered: tool-level runs are free; one full generation suite is a measurable credit spend, so prompts are tuned on a small smoke suite and the full suite runs nightly. The first step is one measured run on one component, to replace the estimates.

5. The stack

underneath
LanguageTypeScript (strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes), Node 22, ESM.
MCPOfficial TypeScript SDK v2 (@modelcontextprotocol/server, client for tests), pinned to an exact version; Zod 4 for tool inputs.
RepoYarn 4 workspaces in an Angular monorepo; the library builds with ng-packagr; the server is a sibling workspace.
TestsVitest: an in-memory client/server pair for tool tests, plus a real stdio spawn test. The MCP Inspector for hand checks. ESLint with typescript-eslint.
Evalspromptfoo, Playwright with axe-core, Storybook stories as render targets.
AgentsThe team's approved agent host for client code. Model choice is a config value, so the eval harness can compare providers on the same cases.

Questions I'd bring to the team

  • Where do agents fail most on your system today? That list becomes the level-2 eval set.
  • Which outputs must a person approve? Gates belong where a mistake is expensive, not everywhere.
  • What can leave your network? That decides hosted versus local for both the server and the evals.
