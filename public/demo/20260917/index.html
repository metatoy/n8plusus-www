    Read the findings report

    Agentic report · 16 Sep 2026, §11 added 17 Sep · written by an agent from the question above, to be read without the originating chat

    Code Simulation: Can agents predict rendered-output impact without building and rendering?

    Findings report. Date: 2026-09-16. Scope: client-side HTML, CSS, and (as a boundary case) client-side scripting. Self-contained: written to be read without the originating chat.

    1. The question, as it evolved

    1. Specific. If a design token changes from white to blue, can an agent say "there is a button with a black background, and blue text on it would be hard to read" before building the project, booting headless Chrome, screenshotting, and analyzing the image?
    2. General. A human engineer remembers how the code looks when rendered and imagines how a change would look. How do we give agents that faculty in a generalized way, scoped to client-side HTML, CSS, and scripting?
    3. Resources. For an average website, if an agent reviewed the codebase and the rendered output, what would it cost to train so it could model the impact of HTML and CSS changes? Assume a two-tier design: an expensive offline process using larger models (WebDreamer, Beyond DOM, MobileDreamer class) that produces a cheap, fast LLM response for the everyday case.

    2. Findings in brief

    • The human faculty is not simulation. A senior engineer does not render the app in their head. They hold a memory of rendered scenes, a sparse causal index from code to appearance, a cheap local imagination applied to a remembered patch, and calibrated doubt about when to go look. Replicating the faculty means replicating those four things, not pixel-level mental rendering.
    • The LLM already has the local imagination. It knows blue on black is low contrast. What it lacks is grounding: a memory of this app and an index linking this variable to that button. Fix memory and index, and most of the imagination is already present.
    • The render is cheap; the loop is expensive. Chrome lays out a page in tens of milliseconds. The cost that hurts is rebuild, boot, screenshot, and a vision model reading a picture back into facts that were available as data. The fix is to render once per commit, capture structurally, and answer every later question from the capture.
    • For HTML and CSS only, training is optional. The browser is a free, exact oracle, so ground truth costs nothing to generate. The one training investment that clearly pays is a small interpretation model that reads a compact scene description plus computed deltas and speaks like a designer. A general "render-delta" model is justified only for never-rendered code, no-browser environments, or design-search loops evaluating thousands of candidates per second.
    • Nobody ships this. Closest shipped thing is Chromatic TurboSnap (selects which stories to re-render; still render-based; cannot say what will go wrong). Closest research is WebDreamer (LLM as world model for web actions), Beyond DOM (layout relations predicted from source without rendering), and MobileDreamer (next GUI state prediction). None predicts the visual consequence of a style change from data before rendering.
    • Excluding client-side scripting is the single biggest cost saver. With no runtime state to explore, the world is deterministic and fully enumerable per state set. The state-transition world model (MobileDreamer class) drops out entirely and returns the day JavaScript is added to scope.

    3. What the human actually does

    Faculty What it is How it formed
    Episodic scene memory Compressed, semantic, hierarchical: "dark header, white cards on gray, black primary button with white text" Looking at the running app many times
    Causal index (code to appearance) Sparse graph: "button text comes from that variable through the primary class" Reading code, and mostly changing things and watching what moved
    Local imagination Propagate the change through the index to a remembered patch, then apply a learned predicate: "blue on black, hard to read" Innate visual priors plus experience
    Calibrated doubt Knows which memories are stale; goes and looks when stakes or uncertainty are high; every look updates memory Being burned

    Humans are bad at predicting the layout of a page they have never seen from its CSS. The advantage is memory of having seen it, plus knowing what matters.

    4. What the LLM is missing (and what it is not missing)

    Missing:

    1. Persistent visual memory of the app. Each session starts blind. Screenshots are consumed as tokens and forgotten across context boundaries. The agent has never "lived with" the app.
    2. A code-to-appearance index. It can grep for consumers on demand, but that is slow and incomplete: cascade, inheritance, runtime class toggling, JS-computed styles.
    3. Calibrated uncertainty about visual state. It will confidently assert what a page looks like from code and be wrong.
    4. Cheap access to the render. The only way to look is the full loop.

    Not missing: the visual-semantic priors. Given a correct, compact description of the current scene, the model's existing judgment ("blue on black is low contrast", "40 characters wrap in a 200 pixel column", "radius larger than half the height becomes a pill") is usable. Research on LLMs predicting program execution (CRUXEval and similar) shows they are mediocre at simulating execution; rendering is execution. The conclusion is: do not have the model simulate, give it tools and memory.

    5. General architecture for client-side web

    Five faculties. Each is buildable today.

    5.1 Structured scene memory, captured as a side effect of every real render
    • Not pixels. The DOM with computed styles and boxes, per route and per state (viewport, theme, hover, focus, data fixtures). Chrome DevTools Protocol DOMSnapshot.captureSnapshot returns the whole document's DOM, computed styles, and layout in one call. Playwright exposes the accessibility tree the same way.
    • Stored on disk keyed by commit, invalidated by build. Alongside it, an LLM-written semantic summary per page, hierarchical like human memory, small enough to sit in context. Keep both: the full snapshot for computation, the summary for reasoning and retrieval.
    • Every screenshot an e2e suite already takes is a wasted capture. Save the structured snapshot next to it and the memory builds itself for free.
    5.2 Dependency graph from source to rendered property
    • Static layer: which rules reference which custom properties; which selectors matched which nodes (from the capture); which component produced which DOM (source maps, React fiber, data attributes); which modules import which (bundler graph, as TurboSnap uses).
    • Dynamic layer: which props and state toggle which classes or inline styles. Learned by perturbation, exactly how humans learn it: change an input in the loaded page, diff the capture, record the edge.
    • Mental model: the rendered page is a spreadsheet where every visual property is a cell with a formula over code. Change an input cell, recompute dependents.
    5.3 Tiered oracle for the effect of a change
    Tier Handles Mechanism Cost
    A. Algebraic color, opacity, border, shadow, font-weight substitution into the provenance graph; predicates are formulas (WCAG and APCA contrast, visibility, border contrast) milliseconds, no browser
    B. Partial layout spacing, size, font-size, copy changes re-run layout on the affected subtree with a fast engine (Yoga, Taffy) using font metrics cached from the capture or read from font files milliseconds to tens of ms
    C. Slice render images, canvas, complex composition keep one browser warm against the dev server; render only the affected route or story; cost is a reload, not a boot hundreds of ms
    D. Perceptual judgment "looks cluttered", "hierarchy is off" vision model on a crop of the affected region, never the whole page one small vision call

    The LLM never emulates a browser. It picks the tier, reads findings, and interprets. Color tokens never move layout, so a stale snapshot is fully valid for tier A. Some geometry is still predictable from the snapshot without layout: radius beyond half the element height clamps to a pill; text width scales near-linearly with font size, so overflow is estimable.

    5.4 Calibrated confidence and a look policy
    • Every finding carries how it was computed: exact (tier A), estimated (tier B), or guessed (model prior).
    • Every scene carries staleness: commit distance, and whether the changed files are in the graph.
    • Policy: verify by real render when confidence is low and stakes are high (shipping); skip when confidence is high and the agent is exploring.
    5.5 Learning from disagreement

    When a real render contradicts a prediction, the graph is missing an edge. Record it. The model of the specific app gets denser over time, which is what a long-tenured engineer has that a new hire does not.

    5.6 The analogy that makes the design obvious

    A type checker does not run the program to find type errors, and it does not imagine running it either. It keeps a symbolic model and checks constraints. A contrast check is a type check for color tokens. It can be pushed to a token type system: declare pairings (text-on-inverse belongs on surface-inverse, the way Material's "on-primary" convention works) and check a proposed change against declared pairs before any snapshot exists.

    6. Prior art, placed honestly

    Work What it does Relevance
    Chromatic TurboSnap Git history plus bundler dependency graph selects which Storybook stories to re-snapshot Closest shipped thing. Selection, not prediction. Their monorepo guidance admits a shared theme file flags everything.
    "Token-aware visual regression" (2026 design-systems writing) Test suites know which components use which tokens and re-validate only those Still selective re-rendering. Does not say what will go wrong.
    stylelint-color-contrast and stylelint issue #786 Static CSS contrast lint Only works when color and background sit in the same rule. Dead end for composed UIs; the core issue closed on that limitation.
    WebDreamer (OSU, TMLR 2025) LLM as world model: imagine the outcome of a web action in natural language, then act. Trained Dreamer-7B matches GPT-4o on the task The method (imagine, then verify) and the evidence that a narrow world model can be small. Targets navigation, not appearance.
    Beyond DOM (AI journal, Sept 2025) Neural model predicts eight spatial relationships between element pairs from HTML and CSS source alone, no rendering Direct render prediction from code, at coarse resolution. Fallback for never-rendered code.
    MobileDreamer (2026) Generative sketch world model predicting next GUI state for mobile agents The state-transition tier. Out of scope while scripting is excluded.
    Design2Code, VisRefiner, UICopilot, ArtifactsBench Screenshot-to-code and generative UI benchmarks Opposite direction. Not render prediction.
    Figma-side plugins (Stark, etc.) Contrast checks inside the design file Design-time, not the running app.

    The gap: "predict the consequence of a style change in the real app, from data, before rendering." No one found is working on it in that form.

    7. Resource estimates

    Assumed average site: mid-size marketing site or app. About 100 routes or stories, a couple thousand DOM nodes per page, a few hundred CSS custom properties, 8 state variants (two viewports, two themes, two interaction states). All figures below are order-of-magnitude estimates, not quotes.

    7.1 Per-site learning (retrieval, not weights)

    The agent's review of the rendered output builds scene memory. Its review of the code builds the provenance index. Neither needs a gradient update.

    Step Mechanism Cost for the assumed site
    Capture Warm headless Chrome; one CDP document snapshot per route and state: DOM, computed styles, boxes, matched rules 800 snapshots; under 10 minutes with 4 browser instances
    Storage Structured JSON, gzipped Roughly 200 MB per commit
    Index Variable to rule to node to component to route, plus the reverse; effective background composited through ancestors Seconds to minutes of CPU
    Semantic summaries Frontier model writes a short hierarchical description per page from the serialized scene About 1M input tokens, once per commit
    Perturbation edges Mutate a variable in the loaded page, re-read computed styles, record what moved 100K samples in under an hour on 8 instances

    Whole pass: under an hour and a few tens of dollars per commit, incremental afterward because only changed routes need recapture.

    7.2 The fast tier: what the small model reads

    Never feed the fast model HTML and CSS source; resolving source to appearance is the browser's job. It gets a scene card for the affected region plus the oracle's computed deltas:

    region: pricing/hero/cta-button   theme: dark   viewport: 390
role: button   box: 160x44   text: "Start free"
text-color:  #FFFFFF  <- --btn-primary-fg <- --color-fg
background:  #000000  effective, own fill  <- --surface-inverse
font: 16px / 600
contrast: 21.0  AA pass

proposed: --color-fg  #FFFFFF -> #1E40AF
oracle:   contrast 21.0 -> 2.4   AA fail   affects 3 regions

    The model turns that into: "the primary button's text goes blue on black and drops well below AA; the same happens on the dark footer links." Input about a thousand tokens. A self-hosted 3B model on one consumer GPU answers in under a second; a hosted small model costs a fraction of a cent. The oracle did the imagining; the model interprets and prioritizes.

    7.3 If you train: three options, ranked
    Option What it buys Data Compute Verdict
    Interpretation fine-tune of a 1 to 3B model Reliable, consistent, designer-voiced findings from oracle output; runs locally 10 to 50K examples generated by a frontier model from real oracle output Single GPU, hours; low hundreds of dollars Do this first, if anything
    General render-delta model, distilled across sites Predicts structured deltas for never-rendered code, without a browser, or at thousands of evaluations per second 5 to 20M perturbation samples across 2 to 10K sites; formula labels (contrast, overflow, occlusion, tap size, visibility) are free; perceptual labels from a vision model on a 200K-crop subset Data generation: hundreds of dollars. Labels: low thousands. A 3B full fine-tune or 7B LoRA on an 8-GPU node: low-to-mid thousands per run, several runs Justified only for design-search loops or no-browser environments
    Per-site fine-tune The site "in the weights", no context needed This site's perturbation samples Cheap per run Not worth it: weights go stale every commit; retrieval is fresh at capture time

    Dominant cost in the second option is engineering, not GPUs: the capture harness, the state matrix, the serialization format, and the eval suite are a small team for a few months. Training compute is a rounding error next to that.

    7.4 Where the three named models fit in the two-tier design
    • WebDreamer contributes the method (imagine in language, then verify) and the evidence that the fast tier can be a small fine-tune. Its architecture is the template for the fast tier, not the expensive one.
    • Beyond DOM is the template for the never-rendered case. In practice a warm browser rendering a fragment in a few hundred milliseconds usually beats it; it wins only when a browser is unavailable or throughput must be extreme.
    • MobileDreamer drops out once scripting is excluded. It is the expensive tier the day JavaScript enters scope.
    • The actual role of an expensive frontier model offline is labeling perception: writing scene summaries and judging crops for qualities that have no formula. Formulas label everything else for free.

    8. Where training genuinely pays

    1. Design-search loops. An agent doing beam search over thousands of style variants wants a millisecond predictor, not a hundred-millisecond render.
    2. No-browser environments. Edge, offline, or restricted sandboxes.
    3. Perceptual judgment. "Looks cluttered", "hierarchy is off": no formula exists, so a learned judge is the only option.
    4. State transitions once scripting is in scope: predicting what the page looks like after the user opens the menu, without executing the app.

    9. What stays hard

    • JavaScript state is the hardest of the three domains. Every state cannot be captured. Humans cope by remembering representative states; agents need state catalogs (stories, routes, fixtures) and harnesses to reach them. This is where the world model eventually matters.
    • Provenance through JavaScript. Dynamic class strings, CSS-in-JS, styles computed from props blur the code-to-style edge. Perturbation learning helps. Build-time-static systems (Tailwind, vanilla-extract, StyleX, Panda) make styles knowable statically, which means those codebases are literally more imaginable. Nobody is making that argument yet.
    • Text measurement outside a browser needs real font metrics: cache from captures, or read font files (opentype.js class tooling).
    • Cross-browser. The snapshot is Chromium. Safari and Firefox differences remain a residual for real rendering.
    • Perception beyond formulas. Contrast, overflow, tap-target size, and z-order occlusion are computable. Aesthetics need a model on a crop.

    10. Recommendation

    Build the capture, index, and oracle with no training and a hosted small model reading scene cards. That delivers the blue-on-black case exactly, fast, and cheap, per site, in about a week of work. Log every query and every verification disagreement. After a few thousand real queries the interpretation fine-tune dataset exists for free, and the disagreement log shows whether the never-rendered case is common enough to justify the distilled render-delta model. Expectation: it is not, because tokens change far more often than the components that consume them.

    One-sentence version: give the agent a visual REPL whose outputs are stored structurally, indexed by code, and never thrown away, and the imagination problem mostly dissolves into a retrieval problem. That memory layer is the general product, and it does not exist as a standalone thing.

    11. If GitHub shipped it: what to charge, and where the value lands

    Added 2026-09-17. Prices are as listed on that date and move; every figure is order-of-magnitude.

    This would not be a product. It is a check inside two things GitHub already sells: Copilot code review, which since 1 June 2026 is metered in AI Credits (1 credit = $0.01, token-priced at API rates) plus GitHub Actions minutes, and Agentic Workflows, which are read-only by default and take exactly the shape of a check. The capture in §5.1 is a side effect of CI that GitHub already runs for the customer.

    Using the §7 figures for the assumed site (about 100 routes, 8 state variants), recapturing only what the diff touches.

    Component Mechanism Cost per check Who pays today

    Recommendation: B for the structural check, A for the perceptual tier, and let Actions bill the capture.     11.3 Where the value lands

    For the customer:

    • It replaces a loop that now costs money every time. A structural answer in milliseconds instead of $0.10 to $0.30 and several minutes per verification, repeated per agent iteration. Under usage-based billing the saving is on the invoice, not in a slide.
    • It catches the class of defect that otherwise reaches review or production. Contrast, overflow, tap-target size, occlusion: computable, therefore exact, therefore never a false alarm of the "looks off" kind. Accessibility is compliance; the European Accessibility Act has applied since June 2025, and the enterprise buyer that pays for FedRAMP and data residency pays for this.
    • A finding in words, not a picture to interpret. "Primary button text drops from 21:1 to 2.4:1 on the dark theme, three regions" is something a reviewer acts on; a screenshot is something a reviewer studies. It is the reviewability that agent-authored pull requests need and mostly lack.

    For GitHub:

    • The data moat. The capture happens where the app is already built: in Actions. Neither Cursor nor Claude Code owns the customer's CI. A structured scene memory per commit is data only the CI provider collects as a side effect, which is Appendix A's argument at platform scale.
    • Its own margin. Agents verifying by screenshot are among the most expensive loops on the platform: vision tokens and minutes, per iteration. A structural oracle answers most questions with no model call at all. Under usage billing that is cost GitHub does not incur and credits the customer does not burn, which is what a "near-term margin headwind" needs.
    • It fits the trust model. It is a check, not a write. It drops into Agentic Workflows without touching the read-only-by-default, allowlisted-writes posture.
    • Scale. 43 million pull requests merge a month. If a tenth touch UI in a repository with CI, that is four million checks a month of a kind no competitor can run, each one making Copilot code review say something the others cannot.
    11.4 What it would take

    The capture step as a first-party Action; a snapshot store keyed by commit; the provenance index of §5.2; the tier A and B oracle; the scene-card interpreter as a Copilot model. As §7.3 says, the compute is a rounding error and the engineering is the cost: a small team for a couple of quarters. The first shippable slice, tier A only, colour tokens and contrast, is a few weeks, because the browser is the free oracle and colour never moves layout.

    Caveats

    • All cost and time figures are order-of-magnitude engineering estimates made on 2026-09-16, not measured runs and not vendor quotes. GPU-hour and API prices move; recompute before budgeting.
    • Prior-art coverage is from web searches on the same date plus the author's knowledge. Absence of evidence that someone ships this is not proof; a focused patent and startup scan would be the next step before betting on it.
  • Accessibility as a workflow, not an audit. Can it be checked as the work is made, so the web gets easier to use as a side effect of building it? Why it is worth researching. Agents now generate interface at a scale no audit can follow, and the buyers who pay for FedRAMP and data residency pay for accessibility too. It is compliance, not polish. A read-only workflow that checks each change as it lands is the shape GitHub’s own Agentic Workflows already take.
  • Workflows that keep learning. A workflow is set up once and left alone. Can it be tuned from its own history at setup, and keep improving as the system around it changes? Why it is worth researching. Actions runs about a billion minutes a week and almost every workflow is written once and never revisited. One that reads its own run history, cost, latency, what failed, and proposes its next version is the missing feedback loop. The correction flywheel in the triage tutorial is the measured start.
  • Adoption at the moment of need. Inside a running system, can an agent notice a practice or a piece of business value that already exists elsewhere in the company, and offer it at the point where someone is most likely to take it? Why it is worth researching. Four in five new developers take Copilot in their first week because it is offered where they already are. The same mechanic can carry a team’s practices and hard-won fixes to the person about to need them. The delivery system is the product.
  • The diagram, in motion. System diagrams work, and some people learn by watching rather than reading. Can an agent build a cheap animation that explains a system, the same walkthrough as the diagram, played rather than read? Why it is worth researching. Thirty-six million developers joined GitHub last year, and most of the code they will touch was written by someone else. Understanding a system you did not write is the bottleneck agents make worse, and an explanation you can watch is cheaper to make than it has ever been.

Three ways I’d change how people work with AI

  • The baseplate, not the bricks. We’re handed new Lego bricks every day, a model, a tool, a protocol, and it is hard to focus on what to build. The work is the baseplate: patterns and frameworks that let a new brick snap into an established way of working instead of starting the build over.
  • Stories that make the abstract graspable. The two-phase triage agent got its shape from a real diagnostic process. My stepson was training as an EMT this summer, and the way a medic classifies severity first and investigates second is the way the agent works now. AI concepts stick when they are grounded in something people already know.
  • Empower creatives, don’t replace them. A designer’s token change previewing live in the running app before anything merges. Wireframes drawn as real Figma frames a person picks from. The tools I build put the person’s judgment at the point where it matters, and let the machine do the rest.
