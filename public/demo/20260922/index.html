Five servers, one protocol

MCP servers I have built, design systems first

Five Model Context Protocol servers, ordered by how much they have to do with design systems. Three of them give an agent a design system to read: which tokens exist, where a colour comes from, which components bind it. One puts an agent inside a gated delivery process. One is a studio knowledge base behind OAuth. Every tool, resource and prompt is named below, with the stack each server runs on, and under that the design-system work they sit on.

In the tool lists, rust marks a write that is gated: it proposes, a person or an entitlement decides.

@sorb/tap

open source · MIT · read-only

Point an agent at a DTCG token file, a Sorb project, or a running Sorb bridge, and it can answer “where does this button colour come from?” with the real alias chain and the components that use it, instead of guessing from a CSS file. Read-only by design, so there is nothing it can break. The smallest of the five and the one meant for other people.

sorb-mcp

Python · FastMCP · reads, gated writes, prompts

The full Sorb server. The same seven reads as the bridge CLI, three writes that are proposals rather than changes, nothing lands without a reviewed pull request or a running preview, plus resources, six workflow prompts and an accessibility skill. Local mode reads the app’s precomputed .sorb/ map with no account and no network. Hosted mode authenticates API keys against Postgres and enforces the write gate per tenant.

sorb mcp, inside @sorb/juice

the first one · on npm

The original Sorb MCP server, a subcommand of the bridge CLI. It exposes the running app’s resolved tokens and component bindings to any MCP client, and it is where the read tools always, write tools only when entitled rule was first built: in hosted mode a read-only session never even sees the write tools in the list, and every call is re-checked at the gate. sorb-mcp above is this surface, ported.

ladder-mcp, the Fidelity Ladder

an agent inside the gate · on PyPI

The ladder is a delivery process where a request climbs from spec to wireframe to preview to build to a merged pull request, and a person approves each rung. This server lets an agent operate that process, under the same governance. A tool may request an advance or file an idea; it can never admit itself, advance itself, or promote to production without a named approver. Those refusals are the thesis, and the code returns them rather than raising.

Knowledgebase MCP

RAG over HTTP · OAuth 2.1

The studio knowledge base, a corpus of specs, decisions and daily digests in Postgres, exposed to agents over MCP. The interesting part is not the retrieval, it is the door: MCP over HTTP as an OAuth 2.1 resource server, with the RFC 9728 discovery document, RFC 8707 resource binding, and a kb.read scope checked on every call. Built as one FastAPI route wrapping the whole tool surface, so the auth contract is testable in one place.

Tools

kb_searchkb_get_summarykb_get_documentkb_digest

 Four reads. Search the corpus, get a document’s summary, get the document, get a day’s digest. No writes; ingestion is a separate collector process, not something an agent can trigger.

The design-system work underneath

  • Sorb : the Figma-to-React token bridge the first three servers read from. Edit a token in Figma, preview it live in a running app before you merge. Four packages on npm and a Figma plugin.
  • Foundation UI : the design system that held at BuzzFeed. A legacy-framework migration, a foundation on the Bootstrap base I shaped, and a component library serving 79 projects, solid enough to build on for four years.
  • The Figma flow : a design system that compiles. Eleven components, three token tiers, six refusals, and an agent whose whole vocabulary is the pack. Storybook, the public Figma file, and the repo are all linked from there.
  • try.sorbcloud.com : Sorb running, no account needed.
