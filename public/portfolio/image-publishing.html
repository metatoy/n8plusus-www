Image Publishing Platform

One image-generation platform, applied in three steps: a server-side rendering engine, a shipped consumer feature built on it, and a self-service concept to make it a paved road for any team.

1 · Dynamic Image-Template Platform

A dynamic image-template platform: server-side React components (styled-components) rendered headlessly into composited PNGs at scale — the engine behind automated social posts and personalized share cards.

  • Pipeline: template receives params → (for content templates) fetches upstream data → renders React server-side → headless Chromium (Puppeteer) screenshots it → composited PNG → uploaded to S3 / served from the CDN.
  • Template registry with version aliasing (v1/v2 → v3 → v4) so old caller URLs keep working while storage paths move forward.
  • Renders the right shapes per surface — 4:5 and 1:1 brand cards, plus OG/social 1200×630, 1080×1080, and 1080×1920 story sizes.

2 · Tag Yourself

A shipped consumer feature: quiz results become personalized share images. A player “tags” their expected result; the reveal generates an “Expectation vs. Reality” card, and the shared link pulls a friend back into the quiz.

  • Share-card layout is driven purely by which results are present (single card · friend/mystery · expectation-vs-reality · a celebratory “you-were-right” variant).
  • A real bug I chased down: Facebook was caching one `og:image` for every share of a quiz result because the “what I picked” id was missing from the canonical URL — so every friend's distinct card collapsed to the first one crawled. Fix: make each pick produce a unique share URL.
  • The redesign won its A/B test decisively (see Results).

3 · Turnkey Sharing

(Concept / proposal — my own design, not shipped.) Turn the proven share-artifact engine into a paved road: a two-pane operator tool (field form + live composited preview) so any team could pick a template, fill content, choose an output shape, and get share artifacts with no engineering ticket — the platform-thinking extension of the gen-media win.

How I built it

Stack: Node.js / Express; templates are server-rendered React 17 + styled-components; rendering via Puppeteer (headless Chromium) + node-html-to-image; fonts embedded as base64 `@font-face`. Caching: image keys are content hashes of the post-processed params, so inputs that render identically share a cached PNG. Testing: Jest + supertest at the HTTP layer.

The platform replaced a legacy Python/wkhtmltoimage service; migration was staged and selective — I ported the ~7 highest-value template families forward from a legacy set of ~48 and dropped the dead ones rather than porting 1:1.

Questions this project answers

What turns a one-off feature into a platform other teams can build on? Separating the engine from the use case. I built a dynamic image-template platform — server-side React rendered headlessly into composited PNGs — and then a shipped consumer feature rode on top of it, with a template registry and version aliasing so old caller URLs keep working as storage moves forward. The platform-thinking extension was a self-service concept: a form-plus-live-preview tool so any team could produce share artifacts with no engineering ticket.

How do you know a redesign actually worked, and not just looked better? You put it to a test with a number attached. The personalized share-card redesign won its A/B decisively — +176% desktop and +82% mobile-web share engagement — and return-visit rate via shared links moved from 59% to 69%. Feeling good about a design is a hypothesis; the A/B result is the evidence.

When you migrate off a legacy system, how do you decide what to bring forward? By value, not by parity. Replacing the legacy render service, I ported the ~7 highest-value template families forward from a legacy set of ~48 and deliberately dropped the dead ones rather than doing a 1:1 rewrite. A migration is a rare license to delete — porting everything faithfully would have carried years of dead weight into the new system.

How do you generate images at scale without redoing the same render over and over? Content-addressed caching. Each image key is a hash of the post-processed parameters, so any two requests that would render an identical PNG share one cached artifact and one render. That's what makes headless-Chromium rendering viable at scale — the expensive step only runs when the output would genuinely differ.
