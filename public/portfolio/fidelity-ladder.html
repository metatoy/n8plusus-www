What I built

Code is the most expensive medium in which to discover you built the wrong thing.

Every agentic coding loop I could find starts at code and verifies correctness — does it compile, do the tests pass. None of them verify direction: whether the thing being built is the right thing. Product teams solved that decades ago, which is why design processes exist at all, and agentic tooling skipped straight to "generate the pull request."

The Fidelity Ladder System puts the ladder back. A request climbs spec → wireframe → prototype → pull request → merge. Each rung produces an artifact a person can judge in seconds rather than minutes, and autonomy is dialled independently per rung — the agent runs free where being wrong is cheap, and gates hard where the blast radius is real.

It is open source under MIT, published on PyPI, and it has opened real pull requests on a real product.

How it works

One file governs an installation: an ANCHOR that states the north star, the non-negotiables, the per-rung autonomy dial, and the budget ceilings. Constraints cascade tighten-only — a run may make a rule stricter, never looser.

A request is admitted, then climbs:

  • Spec — a structured brief whose acceptance criteria are compiled into machine-checkable stubs. Prose that cannot be compiled fails closed rather than pretending to be a gate.
  • Wireframe — real frames in Figma, built by an agent through a deliberately narrow tool surface, then re-linted against what the agent claimed it made.
  • Prototype — a clickable demo against a design system, cheap enough to throw away.
  • Pull request — an agent builds in a worktree, the checks run, and a draft PR opens with the evidence attached.
  • Merge — a person, always. Nothing here merges itself.

Every advance is a human decision with the reasons on screen, and a refused action has to say so — refusals are recorded outcomes, not errors.

How it is governed

The ladder is one half of the system. The other is the console an operator works from — not a dashboard about the runs, but the place every gated decision is actually taken, and the place the rules those decisions are judged against are read from.

Nothing on it is a second source of truth. The policy screens render the installation’s ANCHOR file verbatim, and the one screen that can change policy opens a pull request instead of writing to the running system.

The two surfaces never overlap. A visitor cannot reach this one, and nothing here types into theirs — the console decides, and the ladder is what the decision moves.

How I built it

A Python engine (FastAPI, pydantic) with a React admin, deployed behind Caddy on a small cloud VM.

  • Durable by construction. Runs execute as Temporal workflows, so a restart, a timeout, or a dropped connection resumes instead of losing a climb. Retries check for progress before spending again.
  • Agentic rungs run Claude Code against the Figma and GitHub APIs under declared output contracts — a rung demands fenced JSON and fails loudly when it gets prose instead. An artifact is an artifact; a paragraph claiming one is not.
  • Guardrails are structural, not prompted. The agent's shell is stripped of every credential-shaped environment variable before it starts, tool surfaces are narrowed per rung, and budget ceilings refuse rather than creep.
  • Two-column cost accounting on every run: metered dollars beside a normalised shadow cost, so a subscription lane never hides the real number.
  • The importable core pulls zero web dependencies — pip install fidelity-ladder gets the pattern without the server.

Questions this project answers

  • When should an agent be allowed to proceed on its own? Per rung, earned — free where a mistake costs a glance, gated where it costs a production incident.
  • What does an agentic loop iterate on? Fidelity, not diffs. The cheapest place to be wrong is the earliest one.
  • How do you know the gates work? You measure them. The system ships with its own bench and publishes the number with its bounds attached.
  • What stops a request that should never be built? A refusal that is recorded and explained, rather than a silent success.

Results

  • Real merged pull requests. Requests filed as plain English issues climbed the full ladder and merged into a live product — three merged, five parked at a gate waiting on a person, which is the system working as designed.
  • A measured false-advance rate of ~10% — 7–14% across five clean runs (N=27 seeds, 14 wrong-direction, 3 vessels, two-pass labels). 13 of 14 wrong-direction seeds are caught at or before the rung where they were knowable, and the false-catch control was 7.7%: the judge leaves good work alone. The residual is one characterised blind spot, not noise. Labels were a disciplined second pass by one author, not an independent co-labeller — the number is published with that caveat rather than without it.
  • Open source and installable — MIT on GitHub, fidelity-ladder on PyPI, with the engine's public surface versioned and web-free.
  • A nine-chapter narrated walkthrough (above) that follows one request the whole way, from the problem to the merge.
