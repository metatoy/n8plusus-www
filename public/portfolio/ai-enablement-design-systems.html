AI Enablement for Design Systems

Coding agents write UI that looks right and misuses the design system. I'm building the layer that fixes that: a schema and a contract per component, skills that draft contracts and generate Angular components from them, a Figma matrix that Chromatic can test, an MCP server that serves it all to agents, and the evals and guard rails that keep people in charge.

The problem

Coding agents produce output that looks right and misuses the design system: a token value that doesn't exist, a prop the component never had, the wrong component, an answer that was true a version ago.

The cause is upstream. Figma, the component code, Storybook and the docs each describe the same components separately, and people keep them in sync by hand. An agent reading prose has to guess.

This is current client work, so the client, its people and its code stay off this page. What follows is the approach.

How it fits together

Figma stays the source of truth. Between Figma and the code sits a machine-readable layer: a contract for every component. Agents draft and generate; people review and approve.

  • Figma → contract: an agent skill drafts the contract from the Figma component set, its documentation and the existing code.
  • Contract → component: a second skill generates the Angular component, its tests and its Storybook stories from an approved contract.
  • Contract → Code Connect: the same contract generates Code Connect files, so Figma's developer view shows each component's real code.
  • Contract → agents: an MCP server that follows the contracts' rules gives coding agents in the apps that use the design system deeper knowledge of its components.
  • Apps → Scout → people: Scout, an open-source tool I contribute to, scans those apps for adoption and component usage. That data goes to the people who decide what to improve next.
  • Checks at every arrow: validators compare Figma to contract and contract to code, and visual tests compare the built component to Figma.

Schema design

The schema decides what a contract can say, so it carries most of the design work. Each contract describes one component: props, slots, parts, states, accessibility and behavior rules, the mapping to Figma properties, coverage of every variant combination, and open questions.

  • Platform-neutral core, framework adapter alongside: the same component can be described once and implemented in more than one framework or major version.
  • Open questions are first-class: each carries the assumption the work proceeds on, so nothing waits, but nothing is silently decided either.
  • Approval lives in the contract: one design and one engineering approver, recorded, with a draft status that an agent can never move past.
  • A baseline mode: the same format describes components already in production, so agents get accurate answers about today's library while the next one is designed.
  • Evolves from evidence: when a real case doesn't fit (a state that's designed but deliberately not built, for example), the schema changes on purpose rather than the contract bending around it.

Contract generation

Writing contracts by hand drifts, so writing them is a pipeline: deterministic first, a model second, a person for intent.

  • Extract: read the Figma component set through the REST API, plus the existing code, and record what can be proven.
  • Draft: an agent skill drafts the contract files and lists what it couldn't determine as open questions, each with an assumption. It stops at draft.
  • Validate: schema validation, a Figma-to-contract check, and a coverage check that every variant combination is accounted for.
  • Review: one generated HTML page per batch lets reviewers answer the open questions without reading JSON, then exports their answers back into the contracts.

Angular and Storybook generation

From an approved contract, a component skill generates the Angular component, its unit tests and its Storybook stories to the library's own standards for API, accessibility and testing, then checks its own output and reports.

A contract-to-code validator re-reads the generated component and diffs it against the contract, which doubles as the drift check once the component exists. A small set of proving components, from a divider to a button, exercises the whole path before it's used at scale.

A testable Figma matrix

Figma shows a component as a matrix: every combination of its variant properties. I turn that matrix into Storybook stories, one per cell, generated from the contract's coverage data rather than written by hand.

That makes the design testable. Chromatic snapshots every cell on every change, so a reviewer compares the built component to Figma cell by cell, regressions are caught as visual diffs, and a combination that's designed but never built shows up as a gap instead of a surprise.

The MCP server

A local, read-only MCP server that engineers and designers add to their agent host with one init command. It runs over stdio: no port, no URL, nothing to put through a network security review.

  • Version-correct: it finds the project, resolves the design-system version actually installed there, and answers from that version's contracts.
  • Tools for real questions: list, find and get a contract; find a token, its replacement, or the token for a value; example usage and usage validation.
  • Loud failures: a missing library or an unknown component returns an error that says what was searched and how to fix it, never a "close" match.
  • Built to ship: structured logging on stderr, tests that spawn the real server, and an npm package with a release job.

The harness and its guard rails

The skills run inside an agent harness in Kiro: specs put the work in order, steering files and skills carry the guidance, and hooks enforce the rules in code an agent can't talk its way past.

  • An agent never approves. It can't move a contract past draft or write approval fields; approval is a person's act.
  • Secrets stay secret. API tokens are never printed or passed on a command line.
  • Assumptions are visible. Work continues on stated assumptions, but they stay open until an owner answers them.
  • Small first. Steering that points agents at the shipped theme tokens went out to teams on day one, before the larger pieces landed.

Evals

Without a repeatable score, nobody can tell whether a new skill, prompt or model made the agent better or just different. The eval plan (promptfoo, local and in CI, nothing leaves the network) runs at three levels, cheapest first:

  • Tool accuracy: call the MCP tools directly, no model. Free and deterministic, on every change.
  • Agent + MCP: a headless agent answers real questions, each aimed at a known failure: invented tokens, wrong props, the wrong version.
  • Generation: the agent writes a contract or component in a sandbox with the answers removed, scored against an answer key: build, lint, hidden tests, token use, accessibility, and a round-trip check against the contract.

Deterministic graders come first. An LLM judge scores prose only, and only after it agrees with human raters.

Tools only help if people trust them, so enablement is half the job: getting a consuming team's engineer and designer using the server early, review pages built for designers rather than for JSON, and walkthroughs that explain agent workflows to mixed rooms. Scout

Scout is an open-source adoption dashboard for design-system teams (MIT). Its CLI scans a React, Vue or Angular repository and records every component the code uses, where, and with which props; the dashboard collects those scans across repos, so a team can see adoption at a glance, plan migrations and retirements, and watch each one through. Scans can run in CI on every merge, so the picture stays current.

In this workflow, that usage data is what tells people which components matter most and where the system is being misused, and so what to improve next.

What I added: Angular support, 13 merged pull requests.

  • Finding components in templates: the CLI reads Angular templates and records the components they use, including components that come from installed Angular libraries.
  • Directives: attribute directives are counted where a template writes them, selectors that require an attribute's value match correctly, and a native HTML attribute never makes a directive the owner of an element.
  • Real-world library shapes: reading a library's typings next to its JavaScript, indexing libraries listed only in a shared const array, following const arrays of imports into a template's scope, and counting a component exported under two names once.
  • Groundwork: the scan format accepts any framework name, and the reference graph treats template dialects as one concept, so the next framework is easier to add.
  • Kept honest: a consumer CI job that scans ng-matero, a real Angular app on Angular Material, on every change.

In review: a filter on the component list that shows components with declared props nobody passes.
